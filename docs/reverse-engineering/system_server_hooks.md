# system_server hook audit (CMF Phone 1, Nothing OS 4.1, Android 16)

> **Status (0.70.20):** acted on. The receivers' sender check was added in 0.70.18
> (`Broadcasts.kt`); in 0.70.20 SystemFonts listens once (both constructors are hooked) and
> rewrites the map off the main thread under `mUpdatableFontDirLock`, its class comment now
> says system_server's own map *is* loaded from the rewritten one where the updatable font
> folder exists, and the RotationSensor / SettingsReload comments name the right threads.
> Still to settle on the phone: `getprop ro.apk_verity.mode` (fs-verity, finding 1), whether
> ART inlines the small hooked private methods (finding 8: `dumpsys display` in battery
> saver, AOD rotation, the hidden icon), and Nothing's battery saver states 4-6 (finding 7).

## Answers

1. **BOOT_COMPLETED.** It is sent with `ordered=false` but with a result receiver: UserController.lambda$finishUserUnlockedCompleted$5 (UserController.java:593-604) → Injector.broadcastIntent → `broadcastIntentLocked(..., resultTo, ..., ordered=false, sticky, ...)` (3155). BroadcastRecord.isAssumedDelivered is `receivers[i] instanceof BroadcastFilter && !ordered && resultTo == null` (BroadcastRecord.java:175-176), so for a runtime receiver it is **false**: BroadcastQueueImpl schedules a delivery timeout (832-836) and passes `assumeDelivered=false` to scheduleRegisteredReceiver (889). The receiver gets `ordered=false` in its PendingResult, but the framework still reports finishReceiver after onReceive runs (PendingResult.mAssumeDeliveredHint false), and the system process' broadcast queue waits for it. So it behaves like an ordered delivery: if the Args runnable posted to ControllerHome's handler were removed, the broadcast would stall until its timeout. The current settle() uses `removeCallbacks(APPLY)` only, which no longer drops it. USER_SWITCHED is sent with resultTo=null (UserController.java:2167): assumed delivered.
2. **SaverRefreshRate.** Yes: updateLowPowerModeSettingLocked ends with `updateLowPowerModeAllowedModesLocked()` (DisplayModeDirector.java:877), and that method clears priority 18 itself when not in low power (895) or sets it only when `mVsyncLowPowerVoteEnabled` (882). No second call is needed. Because the call is nested, the module's after-hook on the inner method fires first (removes 18), then the outer after-hook removes 19. Both votes and removals coalesce into one MSG 1 (notifyDesiredDisplayModeSpecsChangedLocked:530-534, `!hasMessages(1)`), so no transient 60 Hz frame from the add-then-remove.
3. **CardOrientation.** Yes: the constructor runs inside ActivityStarter.execute's `synchronized (mService.mGlobalLock)` (ActivityStarter.java:540-561 → executeRequest → Builder.build at 1331/1385/1479). The hook does no file I/O and no reload: `store.get()` is a volatile read; `WidgetApps.handles` is a string compare; `Hooks.log` only with diagnostic logging (logcat, via XposedBridge.log). It runs twice per record (synthetic + private ctor), which is harmless. The ActivityInfo it changes is per-launch: PackageInfoUtils.generateActivityInfo makes a new one per query (450/496), and getActivityInfoForUser copies it for other users (ActivityManagerService.java:18312-18318).
4. **WindowOrientationListener.enable.** The only caller is DisplayRotation.updateOrientationListenerLw (DisplayRotation.java:632), which runs under DisplayRotation.mLock = `service.getWindowManagerLock()` (109). It calls the overriding `DisplayRotation$OrientationListener.enable()` (1422), which only sets a flag and posts. `enable(boolean)`, the method the module hooks, runs later from `run()` → `super.enable()` (1440-1446) on the **android.ui thread** (UiThread.getHandler, 155-156) with **no WM lock**. Inside the method, only the listener's own mLock is taken, and the hook callbacks run outside it. The RotationSensor and SettingsReload comments ("called with its global lock held") are wrong, but harmless: reading without reloading is still right.
5. **SystemFonts.** The constructor is `private FontManagerService(Context, boolean safeMode, CompletableFuture<Void>)` plus a synthetic `-IA` overload, and both get hooked. Of the names tried, only `updateSerializedFontMap()` exists (private, line 345); `updateFontMap` and `updateSerializedFontMapLocked` do not. Typeface.serializeFontMap is called only by FontManagerService:
   - `serializeFontMap(FontConfig)` (353-359): the map handed to apps, used by `initialize()` (when an updatable font dir exists), `update()` and `updateSerializedFontMap()`.
   - `serializeSystemServerFontMap()` (385-387): `Typeface.serializeFontMap(Typeface.getSystemFontMap())`, system_server's own map serialized for apps when there is no updatable font dir (or as a fallback).

   **system_server's own map *is* affected.** At boot, `lambda$new$0` (213-222) calls `setSystemFontMap()` → `Typeface.setSystemFontMap(getCurrentFontMap())` (224-229) whenever `mUpdatableFontDir != null` (fs-verity supported and not safe mode, 232-235). system_server then loads its own Typeface map from the very SharedMemory the hook rewrote. Without fs-verity, system_server's own map comes from `loadPreinstalledSystemFontMap()` (256) and only the copy is changed. A runtime rewrite (rewriteMap) does not call setSystemFontMap, so system_server keeps the font it booted with until the next reboot. Evidence needed from the phone: `getprop ro.apk_verity.mode` (2 = fs-verity), or whether `/data/fonts/config/config.xml` exists / `cmd font update` refuses with "font updater is disabled".
6. **ControllerHome.** `public void systemReady()` (PWM:5323, dex `()V`). `public long interceptKeyBeforeDispatching(IBinder focusedToken, KeyEvent event, int policyFlags)` (2729, dex `(IBinder;KeyEvent;I)J`). `public boolean interceptUnhandledKey(KeyEvent, IBinder)` (3599). HOME is an exclusive role per user. Android's own DefaultAppProvider reads it with `getRoleHoldersAsUser("android.app.role.HOME", UserHandle.of(profileParent(userId)))` (DefaultAppProvider.java:73-74, 106) and sets it with `addRoleHolderAsUser(HOME, pkg, 0, UserHandle.of(userId), executor, callback)` (86). ControllerHome makes the same calls for ActivityManager.getCurrentUser().
7. **HiddenAppIcon.** `private boolean LauncherAppsService$LauncherAppsImpl.shouldShowSyntheticActivity(UserHandle user, ApplicationInfo appInfo)` (LauncherAppsService.java:575), called from getLauncherActivities (526, 541). The class is `static class LauncherAppsImpl extends ILauncherApps.Stub` (159). The signature matches.
8. **Missing or different targets:** none. Every class, method, field and parameter list exists, so no "failed to install …" lines are expected. Differences that change what the module does or logs:
   - CardOrientation logs "widget cards: 2 activity record hooks", and each record is unlocked twice (harmless).
   - SystemFonts' constructor hook fires twice, so two ACTION_FONT receivers are registered (see bug 2).
   - rewriteMap never logs "cannot be rewritten" (the first name exists).
   - The OrientationProbe updateOrientation after-hook fires twice per update (deduped).
   - WakeOrientation's `mEnabled` read hits the subclass field.

## Mismatches / bugs (most severe first)

1. **SystemFonts' claim "system_server's own map is never touched" is false on this build** (FontManagerService.java:213-231, with 252-263). When the updatable font dir exists, system_server loads its own map at boot from the hooked serialized map. A font that breaks text rendering can therefore break system_server itself at every boot; the GUARD/FAILED mechanism is the only protection. After a change, system_server's own map stays the boot one until reboot while apps get the new one. Fix: mark the own-map path so the hook skips it, or call setSystemFontMap only when intended. Evidence needed first: fs-verity on/off (see answer 5).
2. **SystemFonts registers its ACTION_FONT receiver twice** (two FontManagerService ctors hooked, the dex shows Lifecycle → synthetic ctor → private ctor). Each font change runs `reloadAndNotify` + `FAILED.delete()` + a full `updateSerializedFontMap()` twice. Fix: hook only the 3-arg ctor (findAndHookConstructor with Context, boolean, CompletableFuture) or guard `listen()` with `service != null` / once.
3. **SystemFonts' rewrite runs heavy work on system_server's main looper without Android's lock.** The receiver is registered without a Handler (SystemFonts.java:137) and calls `updateSerializedFontMap()`, which Android only calls under `mUpdatableFontDirLock` (initialize/update). It rebuilds every font family (SystemFonts.buildSystemFallback, mmap of all font files) on the main thread, twice (bug 2), and can race a concurrent `update()`. Fix: run it on a background HandlerThread and hold `mUpdatableFontDirLock` (getObjectField(service, "mUpdatableFontDirLock")) as Android does.
4. **Exported system_server receivers never check the sender.**
   - SystemShortcuts.java:65/82/101 (RUNNING_SERVICES, EXPAND_NOTIFICATIONS, OPEN_MEDIA_APP) and SystemFonts ACTION_FONT are `RECEIVER_EXPORTED` and never call getSentFromUid/getSentFromPackage, although the senders attach `Broadcasts.withIdentity()`. The comment in ui/RunningServices.java:40 and launcher/RecentsRam.java:124 says "the system opens it only for the module and the launcher", which is false.
   - Any app can expand the shade or launch the playing app's session activity with system identity and BAL allowed (SystemShortcuts.java:130-134). It can also re-arm a font that crashed system_server (`FAILED.delete()`) and repeatedly trigger the double font rebuild.
   - ACTION_RELOAD receivers (SettingsReload, ControllerHome, SaverRefreshRate) are exported too, but only re-read the settings file or re-run Android's own vote update (low impact).
5. **WakeOrientation reads the wrong `mEnabled`** (WakeOrientation.kt:119, 168). XposedHelpers finds `DisplayRotation$OrientationListener.mEnabled` (DisplayRotation.java:1385, the requested state set on the WM thread) before the base `WindowOrientationListener.mEnabled` (39, the registered state). The result is about the same in practice, and "screen off again" is even detected earlier. To read the base field, use `XposedHelpers.findField(WindowOrientationListener.class, "mEnabled")`.
6. **Comments state a lock that is not held.** RotationSensor.java:44-48, SettingsReload.kt:17 and WakeOrientation's unlock path say enable() runs under the WM global lock. It runs on android.ui without it (answer 4). The code is still right; the course text should be corrected.
7. **BatterySaverSync only knows states 1/2/3.** This build has Nothing's states 4 (pending sticky), 5 (auto-snoozed) and 6 (Nothing's own automatic saver, reason 14, BatterySaverStateMachine.java:328-333, enableBatterySaverLocked:490-525 writes low_power=0 for reason 14). In state 6 the module changes nothing (safe). A switch through the setting while in 4/5/6 is not reconciled. Untested on the phone.
8. **Inlining risk (untested).** The small private hooked methods (`updateLowPowerModeAllowedModesLocked`, `shouldStayEnabledWhileDreaming`, `shouldShowSyntheticActivity`) can be inlined by ART into their callers in system_server's compiled services.jar, and a hook on an inlined method is then bypassed. The module has Hooks.deoptimize, but these features do not use it. Evidence needed: with battery saver on, `dumpsys display` (DisplayModeDirector votes: no PRIORITY_LOW_POWER_MODE_RENDER_RATE vote with the setting on); the AOD rotation behaviour; the hidden icon not coming back as an app-info entry.
9. **CardOrientation runs twice per ActivityRecord** (synthetic + private ctor). Harmless now; worth knowing for the course, and the install log says 2 hooks.
